## 逃生舱（你明确要保留的"直接改模板"）

| # | 决定 | 标签 | 推翻成本 |
|---|---|---|---|
| 15 | patch 存**掩码化的锚定 hunk 列表**，不是 unified diff | `[推断]` | 大：见下 |
| 16 | 掩码文本靠"用同一个模板渲染第二遍"生成，不用字符串搜索 | `[推断]` | 中 |
| 17 | 上下文窗口默认前后各 3 行（现有 preset 只有 1 行，在 `.qci` 里区分度不够） | `[推断]` | 小 |
| 18 | 明确**拒绝**语义化补丁（"把 corner 设为 CBEST"这种） | `[推断]` | 大 |

**第 15 条为什么不用 unified diff**：一条 recipe 天然要跑几十个 cell，
而 diff 的上下文行里全是变量。采集自 `cell=pll_top` 的补丁跑到 `cell=vco_core` 时，
上下文行 `*lvsLayoutPrimary: pll_top` 变成 `vco_core`，`git apply` 必然 reject —— 
**这是最常见场景，不是边缘情况**。更糟的是 `after` 侧：如果你的手工修改里引用了 cell 名，
diff 会把它冻死在补丁里，换 cell 产出错文件**且不报错**（静默错误，最坏的一类）。
掩码格式存成 `${cell}`，重新物化时自动跟上。

**第 18 条为什么拒绝**：语义化补丁就是 knob 换了个名字 —— 它要求我们预先理解每种文件的语法，
等于把"哪些参数能调"重新变成"当初谁写了 parser"。逃生舱的全部意义就是能碰任何东西，
包括我们从没建模过的东西。

**第 19 条被用户推翻，2026-08-24。** 原判断是：`choices_confidence: guess` 的取值集合是在
一台没有 Cadence 的机器上编出来的，做成封闭下拉会给用户一半无效项，还会把唯一能用的拼法藏起来
—— 所以给纯文本框，候选只作为灰字提示。

真人一用就否了：*"很多参数你选择的是 blank 填写，这个并不合理；用户可能不知道正确的写法是什么，
可能填写错的；有限选择的部分应该用下拉框才对。"* 空白框的失败模式比半错的下拉更糟 —— 它不给
任何线索，用户只能凭空编一个拼法，还编错。

新答案两头都要：**可编辑下拉框**（`FreeChoiceOptionEditor`）。候选在下拉里，所以永远有个像样的
东西可选；框本身仍接受任意输入，所以目录猜错也锁不住用户想用的拼法。`NoInsert`，打进去的值不进
候选表（那是这份配方的值，不是新的目录成员），灰字提示改说"这个列表不权威"。

同一条逻辑外推到 `list`：封闭且可信的成员表（`stages`、`output_form`）改成一行复选框
（`MultiChoiceOptionEditor`）—— 让用户去拼 `si, strmout, calibre, quantus, jivaro` 这件事，
没有任何一点是为他服务的。

**这条决定当年是被测试锁死的**（`assert all(editor_kind(opt) is EditorKind.TEXT ...)`）。
测试能保护一个决定，不能验证它是对的；补上的验证层见 `UX_VALIDATION.md`。

**第 21 条的理由**：一份 Recipe 从 8 核机器带到 64 核机器就得改，直接违背

# 追加：自带文件导入 + 模板参数化（2026-08-22）

## 起因

用户问："能不能自己导出一个模板设置，导入软件作为配方之一？"
做这个功能时用一份手写的 `.cmd` 试，暴露出上一轮**没走完的最后一公里**。

## 发现的缺陷

**177 条 catalog 选项里有 84 条 owner=recipe/profile，但模板里那一行还是写死的。**
Recipe 有字段、GUI 能改、改完跑不了 —— 包括用户点名要的 `-technology_corner "TYPICAL"`。

不是静默错误（render 会拒绝并说明），但对用户来说结果一样：**第 3 条抱怨只解决了一半。**

**这个缺口是我自己的验收标准造成的。** C1 我要求"新旧渲染逐字节相同"来证明迁移安全，
而"不动模板"是满足它最省事的路径。那条检查证明了迁移保真，
**却没有证明这东西到底能不能配置** —— 我验证了没变坏，没验证变好了。

教训：验收标准要同时覆盖"没坏"和"做到了"，只有前者会掩盖后者的缺席。

## 修法与结果

| | |
|---|---|
| 缺口 | 84 条 → **1 条**（`lvs_rules_filename_pattern`，结构替换不是字面量替换） |
| 守门 | 缺口归零做成测试 —— 以后加 catalog 行忘了参数化模板会立刻被抓 |
| 验收 | 参数化前先冻黄金样本；改完用默认值渲染必须**逐字节相同**（20/20 通过） |
| 端到端 | profile 加 rcworst → 配方选它 → 渲染出 `-technology_corner "RCWORST"` |

## 修着修着又挖出一个（更危险的）

导入把 `125` 读进了 `temperature_c`，**同时**存了一条把渲染出的 `${temperature}`
槽位替换成硬字面量 `125` 的 patch。后果：用户之后改温度会被 patch 拍回去，
**配方字段变成死的** —— 正是这轮重构要消灭的那类问题，从新功能这条路漏了回来。

根因：`125` 解析成 float 后渲染成 `125.0`，与原文差一个字节，被当成用户的编辑。

修法：float 携带它被解析时的书写形式；没人写过的数（catalog 默认值、计算值）
仍是普通 float，所以黄金样本纹丝不动。corner 则改成**教给派生 profile**
而不是冻进 patch；用户指定真实 profile 时不擅自改人家的表，而是明确报告缺哪个 corner。

**立了一条不变量并做成测试**：
> 一个值只要落进了 Recipe 字段或 Profile，就绝不能同时被 patch 钉住。

手写样本上的效果：patch 从 8 个降到 **2 个** —— 剩下的是工具版本注释行（owner=fixed）
和一整段 `rf_analysis`（我们确实从没建模过）。**这才是 patch 该装的东西。**

## 已知边界（不是 bug，但要知道）

- 配方存盘再加载后，书写形式会丢：导入时文件里是 `125`，
  存进 YAML 是 `125.0`，之后渲染出 `125.0`。数值等价、字段仍然可改，
  只是不再逐字节复刻原文。拼写保真的作用是**防止导入把格式差异误判成编辑**，
  这个目的已经达到。
- 派生的基线 profile **不落盘**（它是导入的产物，不是真 PDK profile）。
  所以导入出的配方若命名了一个你 profile 里没有的 corner，运行时会拒绝并告诉你
  缺哪个、有哪些。这是有意的：宁可让你去 profile 里补，
  也不要往 `config/profiles/` 里堆假 profile。
